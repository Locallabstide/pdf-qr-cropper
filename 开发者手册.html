1项目概览

它做什么

输入一份 PDF，输出一个 ZIP，里面是 PDF 中所有二维码被裁成的正方形 JPG。整个过程完全在浏览器内完成，零网络请求。

技术选型

层方案为什么
PDF 解析与渲染pdfjs-dist 3.11.174业界事实标准，API 稳定，支持 canvas 渲染
二维码识别zxing-wasm 3.0.2WASM 版 ZXing，性能远超纯 JS 实现，且能返回码眼四点坐标
并行执行原生 Web Worker 池检测是纯 CPU 密集计算，必须离开主线程，否则 UI 冻结
ZIP 打包自实现（约 60 行）避免引入 JSZip 等依赖（体积 + 复杂度），格式简单可控
图片编码Canvas toBlob('image/jpeg')浏览器原生，无需编码库
UI原生 DOM + CSS，无框架单文件约束下，框架的构建链代价过高

为什么是"单文件"

目标场景是"发给别人用"。单文件意味着：不用装 Node、不用起服务、不用配 CORS、可以放 U 盘、可以走邮件附件、断网可用。代价是所有依赖必须内联（pdf.js worker 用 <script type="text/plain"> 藏，zxing-wasm 用 base64 塞进 Worker 模板字符串）。

PDF 文件→ pdf.js 渲染成 canvas（300 DPI）→ 降采样到 ≤1800px 检测图→ Worker 池 zxing 识别码眼→ 坐标回映射原图→ 按码眼裁正方形→ JPG 编码→ 自实现 ZIP 打包→ 下载

2设计原则与硬约束

五条不可违反的约束

#约束原因
1 单文件红线
交付产物必须是一个 .html，不能有外链 JS/CSS/WASM/字体/图片		 离线可用 + 可邮件传递。任何 https:// 外链都会破坏这一承诺
2 Worker 代码必须模板字符串安全
Worker 源码整体存在 JS 模板字符串 WORKER_SRC 里		 模板字符串内不能出现裸的反引号和 ${，否则提前闭合。WASM base64 需按行拼接
3 命名必须按页序归位
不能"谁先处理完谁先编号"		 并行执行完成顺序随机。必须用 pageResults[页码] 暂存，最后按页序遍历合并
4 离线校验零外链
发布前必须验证文件内没有 https:// 形式的资源引用残留		 zxing 的 locateFile 默认指向 jsdelivr CDN，必须重写为本地 blob/内联
5 体积预算 ≤10 MB
当前 4.10 MB		 邮件附件、聊天工具的常见限制。超出需重新评估内联策略
⛔ 最容易踩的坑 约束 2：往 WORKER_SRC 里加代码时，如果新代码里写了反引号或 ${}（比如字符串拼接、模板字面量），整个 Worker 会在创建时静默崩溃。表现出来是"检测结果永远是 0"，而不是报错。改动 Worker 代码后务必回归测试。

开发原则

  • 不做无谓的通用化——这是专用工具，不是库。不为"万一以后要用"增加抽象。
  • 失败要显式——宁可报错，不要静默产出空结果（见第 12 章的 S1 修复）。
  • 内存优先——大 PDF 场景下，一次多余的全页拷贝就可能导致 OOM。所有中间 canvas 用完尽快释放引用。
  • 零拷贝优先——Blob 直接拼进最终 Blob，不先转 Uint8Array 再转回来（见 O5 修复）。

6检测引擎：三尺度自适应

这是识别率的核心。函数 detectPage(buf, w, h, mode) 定义在 Worker 内（约 23032 – 23064）。

常量

常量值含义
DET_LONG_MAX1800检测图最长边上限（px），与导出分辨率解耦
MAXP100000000 (1e8)Worker 内允许的最大像素数，超限则跳过该尺度
去重阈值0.6中心距 < min(side)×0.6 视为同一个码

算法骨架

async function detectPage(buf, w, h, mode){
  const MAXP = 100000000;
  const skip2x  = (mode === '1x');
  const force3x = (mode === 'full');

  /* ---- 第 1 轮：原尺寸 ---- */
  let l1 = []; try{ l1 = await runDetect(new Uint8ClampedArray(buf), w, h); }catch{ l1 = []; }
  const a1 = parse(l1, 1);
  const c1x = a1.length;

  /* ---- 第 2 轮：放大 2 倍 ---- */
  let merged = a1, c2x = c1x, added2 = [];
  if(!skip2x && w*h*4 <= MAXP){
    const up = upscale(buf, w, h, 2);
    let l2 = []; try{ l2 = await runDetect(up.data, up.width, up.height); }catch{ l2 = []; }
    added2 = parse(l2, 2);
    merged = dedup(a1.concat(added2));
    c2x = merged.length;
  }

  /* ---- 第 3 轮：放大 3 倍（条件触发）---- */
  const need3x = force3x
              || (added2.length > 0 && merged.length > c1x)   // 2x 找到了新的
              || (c1x === 0);                                // M3：1x 全空，强制救援
  let found = merged, used3x = false, c3x = c2x;
  if(need3x && w*h*9 <= MAXP){
    used3x = true;
    const up = upscale(buf, w, h, 3);
    let l3 = []; try{ l3 = await runDetect(up.data, up.width, up.height); }catch{ l3 = []; }
    found = dedup(merged.concat(parse(l3, 3)));
    c3x = found.length;
  }

  /* ---- 阅读顺序排序 ---- */
  found.sort(function(a,b){
    if(Math.abs(a.cy-b.cy) > (a.side+b.side)/4) return a.cy-b.cy;  // 不同行：上先
    return a.cx-b.cx;                                                  // 同行：左先
  });
  return {found, info:{c1x, c2x, c3x, used3x}};
}

三尺度策略的设计取舍

情况1x2x3x总扫描次数
大码文档（常见）✓ 全找到跳过跳过1
大小混合✓ 找到大的✓ 找到小的✓ 兜底3
整页小码（1x 全空）✓ 0 个✓✓ 救援3
mode='1x'✓跳过跳过1
mode='full'✓✓✓ 强制3

相比"无条件跑 3 个尺度"（3 次整页扫描），这个策略在典型场景下只需要 1 次，理论提速约 3 倍，同时保留了多尺度对小码的覆盖能力。

内存护栏

2x 条件：w * h * 4 <= MAXP      // 放大后像素数 × 4 字节
3x 条件：w * h * 9 <= MAXP      // 面积按倍数平方增长

例：检测图 1800×2400 = 432 万像素，3x 为 3888 万像素 × 4 = 1.55 亿字节 > 1e8 → 跳过 3x。这防止超大页在 Worker 内 OOM 导致整个池崩掉。

parse()：从 ZXing 结果提取几何

// 23007 – 23020
function parse(list, f){
  const out = [];
  for(const item of list){
    if(!item.position) continue;                      // 无坐标的丢弃
    const p = item.position;                          // 码眼四点
    const xs = [p.topLeft.x, p.topRight.x, p.bottomRight.x, p.bottomLeft.x];
    const ys = [p.topLeft.y, p.topRight.y, p.bottomRight.y, p.bottomLeft.y];
    const minX = Math.min(...xs), maxX = Math.max(...xs);
    const minY = Math.min(...ys), maxY = Math.max(...ys);
    out.push({
      cx: (minX+maxX)/2/f, cy: (minY+maxY)/2/f,          // 中心（除以放大倍数还原）
      side: Math.max(maxX-minX, maxY-minY)/f,             // 外接方框边长
      minX: minX/f, maxX: maxX/f, minY: minY/f, maxY: maxY/f,
      data: item.text                                     // 解码内容（本工具不消费）
    });
  }
  return out;
}

dedup()：跨尺度去重

// 23022 – 23030 —— O(n²)，但 n 通常是几十量级，可接受
function dedup(arr){
  const out = [];
  for(const m of arr){
    let dup = false;
    for(const u of out){
      if(Math.hypot(u.cx-m.cx, u.cy-m.cy) < Math.min(u.side, m.side) * 0.6){ dup = true; break; }
    }
    if(!dup) out.push(m);
  }
  return out;
}

阈值用 0.6 × 较小边长而非固定像素值——这样对大小不一的码都成立。选 0.6 是因为：同一码被不同尺度检测出的中心偏移通常很小，而相邻两个独立码的中心距至少是 1 倍边长。

💡 顺序敏感 dedup 保留先出现的。因为 a1.concat(added2)，所以 1x 的结果优先保留——1x 在原始分辨率上检测，几何精度更高。这是有意的。

7Web Worker 检测池

检测是纯 CPU 密集任务。如果放主线程，会冻结 UI（进度条卡住、按钮点不动）。这工具的做法是开一个 Worker 池。

为什么不是"每页一个 Worker"

创建 Worker 并加载 WASM 有固定开销（几十毫秒到上百毫秒，含 wasm instantiate）。如果每页临时创建、用完销毁，页数多时开销会累积。所以用常驻池 + 任务队列。

DetPool 类结构

成员作用
workers[]所有存活的 Worker
idle[]空闲 Worker 栈（LIFO 取，热缓存友好）
waitQ[]排队中的任务（无空闲 Worker 时入队）
mapid → job，消息回来时定位对应 Promise
seq自增任务 ID
_url由 WORKER_SRC 生成的 Blob URL，所有 Worker 共用

池大小

// 23158 – 23166
function getDetPool(){
  if(!workerEnabled) return null;
  if(detPool) return detPool;
  try{
    const n = Math.max(2, Math.min(8, navigator.hardwareConcurrency || 4));
    detPool = new DetPool(n);
  }catch(e){ workerEnabled = false; detPool = null; }
  return detPool;
}

钳制在 2–8：下限 2 保证至少有点并行度；上限 8 避免在 32 核机器上开一堆 Worker 抢内存（每个 Worker 一份独立的 WASM 实例堆）。

任务提交与调度

// 23145 – 23156
submit(buf, w, h){
  return new Promise((resolve, reject) => {
    if(this.workers.length === 0){                    // 兜底：池已空
      reject(new Error('所有检测 Worker 均已失效且无法重建'));
      return;
    }
    const job = {buf, w, h, resolve, reject};
    const wk = this.idle.pop();
    if(wk) this._run(wk, job);        // 有空闲：直接跑
    else   this.waitQ.push(job);     // 全忙：排队
  });
}

零拷贝传输

// 23136 —— transferable 语义，buffer 所有权移交，不复制
wk.postMessage({id, buf: buf, w: job.w, h: job.h}, [buf]);

把 ArrayBuffer 放进 transfer list，浏览器做"所有权转移"而非结构化克隆，零拷贝。代价是主线程这一侧的 buffer 会变成 detached（长度 0），所以不能复用——这就是为什么 processOnePage 每次都要重新 getImageData。

注意 imageData.data.buffer 传过去后，重试逻辑（23245）必须再取一次 getImageData，正是这个原因。

崩溃自愈机制

Worker 可能因为：顶层脚本语法错误、WASM OOM、消息反序列化失败而静默死亡。若无处理，挂在上面的 Promise 永远不 resolve，进度条永久卡死。

// 23098 – 23125
const onWorkerFailure = () => {
  const dead = wk;
  this.workers = this.workers.filter(w => w !== dead);
  const idleIdx = this.idle.indexOf(dead);
  if(idleIdx !== -1) this.idle.splice(idleIdx, 1);
  /* 1. reject 该 worker 上所有未完成任务 */
  for(const [id, job] of [...this.map]){
    if(job.wk === dead){ this.map.delete(id); job.reject(new Error('检测 Worker 异常终止')); }
  }
  /* 2. 新建替补，并立即消化队列（否则替补后无人 _dispatch，队列永久悬挂）*/
  try{
    this._spawn();
    const idleWk = this.idle.pop();
    const nextJob = this.waitQ.shift();
    if(idleWk && nextJob) this._run(idleWk, nextJob);
    else if(idleWk) this.idle.push(idleWk);
  }catch(e2){
    for(const job of this.waitQ.splice(0)) job.reject(new Error('无法创建检测 Worker'));
  }
};
wk.onerror = onWorkerFailure;
wk.onmessageerror = onWorkerFailure;
✅ 三层防线 ① onerror 捕获脚本级崩溃；② onmessageerror 捕获结构化克隆失败；③ submit 里 workers.length === 0 的兜底 reject。三层任一生效都能保证 Promise 不会永久悬挂。

8码眼定位与正方形裁切

渲染：PDF 坐标 → 像素

// 11427 – 11438
async function renderPage(page, dpi){
  const scale = dpi / 72;                     // PDF 内部单位是 1/72 英寸
  const viewport = page.getViewport({scale});
  const canvas = document.createElement('canvas');
  canvas.width  = Math.ceil(viewport.width);
  canvas.height = Math.ceil(viewport.height);
  const ctx = canvas.getContext('2d', {willReadFrequently: true});
  ctx.fillStyle = '#fff'; ctx.fillRect(0, 0, canvas.width, canvas.height);   // 白底
  await page.render({canvasContext: ctx, viewport, background: '#fff'}).promise;
  return canvas;
}

要点：

  • scale = dpi / 72——因为 PDF 的坐标单位是 1/72 英寸，而 DPI 是"每英寸点数"。
  • 先填白底——PDF 页面本身可能没有背景，不填白的话透明区域在后处理里会变成黑。
  • willReadFrequently: true——提示浏览器这个 canvas 会被频繁 getImageData，让它用 CPU 后端而非 GPU，避免每帧回读的巨额开销。

A4 = 2480 × 3508 验算

例：A4 为 210mm × 297mm ≈ 8.268in × 11.693in。300 DPI 下：

8.268  × 300 ≈ 2480 px
11.693 × 300 ≈ 3508 px

与印刷行业标准 A4@300DPI 尺寸吻合，说明 dpi/72 换算正确。

裁切算法

// 23169 – 23187
function cropQRSquare(sourceCanvas, qr, padding = 0.06){
  const side = Math.round(qr.side * (1 + padding * 2));   // 四周各留 6%
  const cx = qr.cx, cy = qr.cy;
  const left = cx - side/2, top = cy - side/2;

  const out = document.createElement('canvas');
  out.width = out.height = Math.max(1, side);              // 正方形
  const octx = out.getContext('2d');
  octx.fillStyle = '#fff'; octx.fillRect(0, 0, out.width, out.height);

  /* 源区域与目标偏移：处理越界（码贴近页边）*/
  const sx = Math.max(0, Math.floor(left));
  const sy = Math.max(0, Math.floor(top));
  const sw = Math.min(sourceCanvas.width,  Math.ceil(left + side)) - sx;
  const sh = Math.min(sourceCanvas.height, Math.ceil(top  + side)) - sy;
  const dx = sx - left, dy = sy - top;                    // 保留亚像素偏移

  if(sw > 0 && sh > 0){
    octx.drawImage(sourceCanvas, sx, sy, sw, sh, dx, dy, sw, sh);
  }
  return out;
}

越界处理的设计

如果二维码紧贴页面边缘，裁切框会超出画布。做法是：

  1. 白底先铺满整个输出 canvas；
  2. 源区域裁剪到画布范围内（sx/sy/sw/sh 钳制）；
  3. 用 dx/dy 把源块画在正确的位置上，让缺的部分保留白色。

结果：即使码在角落，输出依然是完整正方形 + 白边，不会变形或拉伸。

💡 padding 为什么是 0.06 ZXing 返回的 side 是四个码眼的外接方框，等于二维码本体大小。二维码标准要求四周有"静区（quiet zone）"才容易扫。留 6% 既保证静区，又不会让图片显得空旷。

检测图降采样

// 23219 – 23232
const longSide = Math.max(canvas.width, canvas.height);
const DET_LONG_MAX = 1800;
if(longSide > DET_LONG_MAX){
  const ds = DET_LONG_MAX / longSide;
  detW = Math.round(canvas.width * ds);
  detH = Math.round(canvas.height * ds);
  const dc = document.createElement('canvas');
  dc.width = detW; dc.height = detH;
  const dctx = dc.getContext('2d', {willReadFrequently: true});
  dctx.imageSmoothingEnabled = true;
  dctx.imageSmoothingQuality = 'high';                       // 高质量降采样
  dctx.drawImage(canvas, 0, 0, detW, detH);
  detCanvas = dc;
}
const invScale = canvas.width / detW;                     // 回映射系数

为什么检测要降采样？

  • 300 DPI 的 A4 是 2480×3508 = 870 万像素。ZXing 的 tryHarder 模式在这个尺寸上很慢。
  • 降到 1800px 长边约 4.6 倍面积压缩，速度快一个数量级。
  • 关键：裁切用的还是原始高分辨率 canvas，所以输出图片质量不受影响。
  • 1800 这个值是权衡结果：再低会开始丢小码（ZXing 需要足够的模块像素）。
⚠️ 分辨率解耦是这个工具的核心设计 "检测用低分辨率（快）"和"导出用高分辨率（清楚）"是两件独立的事。DET_LONG_MAX 只管前者；后者由用户选的 DPI 决定。改动时不要混为一谈。

阅读顺序排序规则

found.sort(function(a, b){
  if(Math.abs(a.cy - b.cy) > (a.side + b.side)/4) return a.cy - b.cy;
  return a.cx - b.cx;
});

行阈值 (a.side+b.side)/4 的作用：如果两个码的垂直中心差小于码宽的四分之一，就认为它们在同一行，改用水平位置排序。

为什么要这样？看这个场景：

码A: cx=100, cy=200
码B: cx=300, cy=205     // 视觉上明显和 A 同一行，但 cy 略低
码C: cx=100, cy=300

纯按 cy 排序会得到 A、B、C（碰巧对）；但如果 B 的 cy 是 199，就变成 B、A、C——明明是同一行，顺序却反了。加了行阈值后，A 和 B 判定为同行，按 cx 排成 A、B，然后才是 C。符合人的阅读直觉。

10零依赖 ZIP 打包器

ZIP 格式本身很简单，手写只要约 60 行，比引入 JSZip（约 100KB）划算。

一个 ZIP 文件的三段结构

[LFH₁ + 数据₁] [LFH₂ + 数据₂] … [CDH₁ CDH₂ …] [EOCD]
缩写签名作用
LFH0x04034B50Local File Header，每个文件一个，后跟原始数据
CDH0x02014B50Central Directory Header，全部集中在文件末尾
EOCD0x06054B50End of Central Directory，文件数 + 目录偏移，解压器从这里开始读

CRC32 实现

// 11373 – 11386
function crc32(buf){
  if(!crc32.table){
    const t = new Uint32Array(256);
    for(let n = 0; n < 256; n++){
      let c = n;
      for(let k = 0; k < 8; k++) c = (c & 1) ? (0xEDB88320 ^ (c >>> 1)) : (c >>> 1);
      t[n] = c >>> 0;
    }
    crc32.table = t;                                   // 表只建一次，缓存在函数属性上
  }
  let crc = 0xFFFFFFFF;
  for(let i = 0; i < buf.length; i++)
    crc = (crc >>> 8) ^ crc32.table[(crc ^ buf[i]) & 0xFF];
  return (crc ^ 0xFFFFFFFF) >>> 0;
}

标准 CRC-32（多项式 0xEDB88320，即反射后的 IEEE 802.3）。256 项查表，O(n) 处理。用 crc32.table 缓存表而不是模块级变量，是刻意的——函数自带缓存，不污染外部作用域。

buildZip 关键片段

// 11393 —— UTF-8 文件名 flag（M2 修复的核心）

bit 11 = 1 表示"文件名是 UTF-8 编码"。没有这一位，中文文件名在解压时会是乱码。

return new Blob([...localParts, ...centralParts, end], {type: 'application/zip'});

为什么不做压缩

LFH 里的 compression method 写的是 0（store，不压缩）。原因：JPG 本身已经是高压缩格式，再套 deflate 几乎压不动（通常只能再减 1–3%），但 CPU 开销很大。所以选择 store，整体更快。

⚠️ 如果改成压缩 需要设 method = 8（deflate），并处理 CompressionStream('deflate-raw')。注意必须是 deflate-raw 而不是 deflate——ZIP 用的是裸 deflate 流，不带 zlib 头。用错了解压会失败。

进度反馈与让出主线程

// 11415

  onProgress(i+1, files.length);
  await new Promise(r => setTimeout(r, 0));      // 让出主线程，UI 能刷新
}

每 5 个文件让出一次。这样进度条能动、页面不假死。间隔 5 是为了平衡"反馈流畅度"和"setTimeout 的 4ms 最小开销"。

16 位字段溢出风险

EOCD 的文件数（offset 8/10）和 CDH 的某些字段是 16 位，最多 65535。f.setUint16(8, files.length, true) 在文件数超限时会静默截断。

实际上不会触发：单份 PDF 提取的二维码数量极少超过几千。但如果要做 Zip64 扩展（>4GB 或 >65535 文件），需要新增 Zip64 EOCD 记录。当前不做，属已知边界。

页数并发的收益边界

并发页数 2 → 3 → 4 的加速比大致是 1.7× → 2.2× → 2.6×（达不到线性），原因：

  • 检测侧 Worker 池大小是 CPU 核数决定的，页并发超过核数后检测开始排队。
  • 渲染在主线程，多页渲染其实是"分时"而不是"同时"。
  • 内存带宽和 GC 成为瓶颈。

Promise / async全流程不可用
String.prototype.padStart编号格式化不可用（ES2017）
💡 file:// 协议下的限制 双击打开时页面运行在 file:// 协议下。这个环境下 Blob URL 正常工作（pdf.js worker 和检测池都依赖它），但如果浏览器策略收紧（如某些企业版策略禁止 file:// 下的 Worker），会触发 S1 的显式报错。
兜底方案：起一个本地静态服务器（python -m http.server）用 http://localhost 打开，或使用 Chrome 的 --allow-file-access-from-files。

离线打包的四件事

  1. 内联 pdf.js——把 pdf.min.js 的 UMD 产物原样插入 <script>（保留 license 头）。
  2. 内联 pdf.js worker——把 pdf.worker.min.js 放进 <script type="text/plain" id="__pdfWorkerCode">，运行时读 textContent 转 Blob URL（代码 11275–11281）。
  3. 内联 zxing-wasm——WASM 二进制转 base64，按行拼接塞进 WORKER_SRC 模板字符串。这是 4 MB 体积的主要来源。
  4. 重写 locateFile——zxing 默认从 jsdelivr 拉 wasm，必须改成从内联数据加载，否则断网失效。
zxing 默认（会被离线校验拦下）:
https://fastly.jsdelivr.net/npm/zxing-wasm@3.0.2/dist/reader/zxing_reader.wasm

构建命令

python .offline-build/build-offline.py

脚本负责：读取各依赖 → 内联 → 生成 pdf-qr-cropper-offline.html → 校验。

16扩展指南

要支持条形码（一维码）

改 runDetect（23002–23005）里的 formats：

// 当前：只认 QR Code
{tryHarder: true, formats: ['QRCode'], maxNumberOfSymbols: 255}

// 改成：二维码 + 常见一维码
{tryHarder: true, formats: ['QRCode', 'Code128', 'Code39', 'EAN13'], maxNumberOfSymbols: 255}

但注意：裁切逻辑假设了正方形（cropQRSquare 用 Math.max 取外接方框）。一维码是长条形，按正方形裁会切掉两端。需要新增一个按检测类型分派的裁切函数，用 minX/maxX/minY/maxY 直接裁矩形（这些字段已经存在，只是当前没用）。

要支持输出 PNG

// 23309 缩略图
img.src = r.canvas.toDataURL('image/png');

// 23368 导出
const blob = await new Promise(resolve => r.canvas.toBlob(resolve, 'image/png'));
/* 并同步改 name 后缀与重名检测正则 /\.jpg$/i → /\.png$/i */

PNG 是无损格式，体积会大很多（二维码图通常 5–10 倍），但边缘更锐利。如果需要，建议做成下拉选项而不是替换。

要支持多 PDF 批处理

当前架构是"单文件单次"。要扩展需要：

  1. 把 currentPdf / currentFileName 改成数组或队列。
  2. 合并循环的 pageResults[页码] 改成 [文件索引][页码] 二维暂存。
  3. ZIP 内按文件建子目录（需要在文件名里放 文件夹/，ZIP 格式支持）。
  4. 最省事的方案：不改架构，让用户依次处理，导出时把「起始编号」衔接起来，最后自己合并 ZIP。

要支持多尺度参数化

当前尺度是硬编码的 1/2/3。如果要做成可配置：

// 把 detectPage 里的 2、3 抽成参数
async function detectPage(buf, w, h, mode, scales = [1, 2, 3])

但要注意 MAXP 检查是 w*h*4 / w*h*9 的硬编码，需要改成 w*h*s*s。

要调 DET_LONG_MAX

值效果
1200更快，但小码（尺寸 < 约 40px）开始漏检
1800默认，平衡点
2400小码识别率提升，检测耗时增加约 78%

要改裁切留白

cropQRSquare(canvas, qr, 0.06)   // 默认四周各 6%

调大到 0.1 会更宽松（静区更足），调小到 0.02 更紧凑（贴边）。不建议低于 0.02——二维码标准要求静区。

要加 OCR 提取二维码内容

检测结果里 qr.data 已经是解码出的文本内容（ZXing 顺手解了），当前只是没消费。要做的话：

  1. 在 results 里保留 qr.data（已经在）。
  2. 加一列 UI，把内容显示/可复制。
  3. 可选：导出时生成一个 index.csv（文件名, 页码, 内容），一起塞进 ZIP。

注意：如果二维码内容是二进制或含不可打印字符，需要做转义。

控制台验证脚本

① 检查 Worker 是否正常创建 
const p = getDetPool();
console.log('池大小', p ? p.workers.length : 'null（Worker 不可用）');
console.log('空闲数', p ? p.idle.length : '-');
预期：池大小 = CPU 核数（钳制 2–8），空闲数 = 池大小。
② 单独测试一次检测提交 
// 造一个纯白 100x100 图提交，预期返回空数组而非报错
const c = document.createElement('canvas');
c.width = c.height = 100;
const cx = c.getContext('2d');
cx.fillStyle = '#fff'; cx.fillRect(0,0,100,100);
const d = cx.getImageData(0,0,100,100);
getDetPool().submit(d.data.buffer, 100, 100)
  .then(r => console.log('OK，返回', r.length, '个'))
  .catch(e => console.error('失败：', e));
预期：打印 OK，返回 0 个。若 5 秒无响应 → Worker 池挂了。
③ 验证 CRC32 实现正确 
// 标准测试向量："123456789" 的 CRC32 = 0xCBF43926
const b = new TextEncoder().encode('123456789');
console.log(crc32(b).toString(16).toUpperCase());
// 预期：CBF43926
不对的话，ZIP 会损坏或解压报 CRC 错误。
④ 检查结果数组的一致性 
console.log('结果数', results.length);
console.log('页码单调', results.every((r,i) => i===0 || r.page >= results[i-1].page));
console.log('名字唯一', new Set(results.map(r => r.name)).size === results.length);
// 名字唯一性在导出阶段才会自动避让，此处 false 属正常
⑤ 验证 ZIP 结构完整性 
// 导出后在 DevTools 里检查下载的 blob
// 最可靠的方法：解压后看文件数是否等于 results.length
// 快速自检：读末尾 22 字节确认 EOCD 签名
async function checkZip(blob){
  const tail = new Uint8Array(await blob.slice(-22).arrayBuffer());
  const dv = new DataView(tail.buffer);
  console.log('EOCD 签名', dv.getUint32(0, true).toString(16));  // 预期 6054b50
  console.log('文件数', dv.getUint16(10, true));
}
